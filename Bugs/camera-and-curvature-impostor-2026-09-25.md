## CAM-PR28-001 — Ship is cut off or camera intersects the ship mesh

**Status:** user observed; visible frame coverage issue, precise root cause unverified. **Priority:** P0 visual polish.

**Actual:** In a High Front Left view the large yellow fallback ship extends beyond the main viewport, in one screenshot to the top/right. The camera's ship-relative fixed 15 ft forward / 10 ft left / 14 ft above offset looks too close for the current displayed mesh at some attitudes/scales. Flying, turning or camera switching can create a composition in which the craft is not fully visible. User reports everything else is working beautifully so far.

**Expected:** Each default shot should frame the *entire visible ship*, including its projected silhouette and configurable margin, at normal supported flight attitudes, while preserving that shot's distinctive left/front/overhead/low perspective. Exceptions are deliberate close-ups or explicit creator-authored overrides. Do not hardcode an assumption that all GLBs have the sphere fallback's size or pivot.

**Candidate causes to investigate (not proven):** numerical camera distance in feet vs actual mesh units; the fallback/GLB display-scale multiplication at altitude; camera aim point at `pilot.y+.25` instead of visible mesh center; near clipping; pose smoothing/ship banking; lack of model-bounds/FOV/aspect-aware framing and of inside-mesh avoidance. Inspect `src/cinematic-cameras.js`, `src/main.js`, `cinematicShipScale`, GLTF loading, near/far logic and current preview viewport aspect before adjusting any preset.

**Proposed fix:** compute authoritative *rendered ship* bounding box or bounding sphere in the active visual frame (including display scale and transformations), select stable configurable aim anchor, derive a minimum viewing distance from actual bounding sphere plus main/preview aspect/FOV with configurable safe margin, and/or adapt FOV and offset appropriately. Maintain original authored offsets and expose a separate reversible `autoFrame` / `minDistance` / safe-area correction—do not silently overwrite the numerical preset or wrongly label it `(Modified)` because an automatic runtime safety correction happened. Update/validate framing on GLB load, scale change, camera swap, view resize, banking and flight-to-ground mode changes when implemented. Avoid per-frame expensive full mesh traversal; cache/update bounds on relevant changes. Respect intentionally authored close shots and allow opting out of safety correction.

**Verification:** Test all six shots at default and customized values with the sphere and a realistically sized imported GLB, at Current/Bigger/Massive, low and high altitude, turns/banks/pitch, main and preview roles, resize and UI overlays. Ensure ship remains visible unless intentionally overridden, movement state does not reset, and default visual composition is appealing.

## VIS-LOD-001 — Floating-island 2D images point down instead of obeying local planetary curvature

**Status:** **user-observed** at ~ALT 433–441, Current 500×500, legacy Forward view; **confirmed in code:** `src/island-impostors.js` generates medium/far cards as `THREE.Sprite` and positions them at wrapped object X/Z/Y with no curvature-aware local-up/orientation computation. **Priority:** P0 visual consistency, include in focused pre-merge pass.

**Actual evidence:** At high altitude, the physical terrain/world appears as a curved blue globe while a small 2D floating-island image nearer its lower/off-center edge keeps its own image/base orientation pointing down the display rather than oriented radially with the corresponding apparent world surface. The image faces the viewer (desirable) but its base does not visually aim toward the world's center. This makes the distant island feel pasted onto the screen instead of belonging to the curved world. Orientation may also be inconsistent across V/legacy and cinematic shots, including the preview. Images show the visual mismatch; they do **not** establish whether only sprite roll, visual position, terrain curvature offset or all three are wrong.

**Current code constraints:** `islandDistanceBands` fades from real mesh to mid and far representations at camera-to-island distances (98–137, 222–280); `graphic()` synthesizes one stylized 160×160 *side-ish* picture from the island's authoritative material/height data, not a view-correct capture of arbitrary mesh geometry; `createIslandImpostors()` uses `THREE.Sprite` (full camera-facing material) and `updateIslandImpostor()` positions sprites using wrapped Cartesian world positions. `src/main.js` also applies world/horizon curvature and a floating-origin position transform to terrain and islands. Verify the actual `src/horizon.js` / `positionIslandVisual` contracts before designing a curvature correction. A true radial `planet center` must not be assumed if the rendered sphere is a visual approximation of the flat semantic map.

**Expected default:** at each island position, derive the local surface *visual up* from the same curvature/transformation that defines the apparent ground. Orient the 2D proxy so its base lies tangent to that surface while the island rises along local outward/up—equivalently the island's base direction points toward the apparent planet center. Independently rotate its image horizontally toward the camera as much as feasible. Preserve correct wrapped semantic position, apparent height, size and LOD fade between the mesh and 2D representations. At directly overhead angles, do not force a side-profile illustration to masquerade as a geometrically correct top view.

**Proposed immediate solution:**
1. Trace real mesh, impostor and curvature transforms at the same wrapped semantic island point and compare the final rendered anchor, local tangent and up vectors. Use a shared, testable visual-curvature transform or derivative/local tangent; no invented second sphere or physics/navigation rewrite.
2. Replace unrestricted `THREE.Sprite` with a lightweight billboarded quad or similarly controlled proxy if full 3D orientation of the 2D plane is required. Choose local up = outward-from-visual-ground; project camera direction into that local tangent plane to derive horizontal-facing direction; build an orthonormal basis. Handle degenerate near-overhead viewing when camera direction nearly parallels local up via stable prior rotation or explicit alternate view. Include correct ordering with ship/global floating origin, world wrap and renderer's visual bend.
3. Do not simply rotate the image on the screen or pivot around global Y; verify the *bottom/base* and anchor remain on the expected apparent world surface at every altitude. Check that physical 3D island and 2D proxy share local orientation and bend so no discontinuity occurs during crossfade.
4. Reuse current bounded texture/material/LOD pools and avoid per-frame canvas regeneration or expensive mesh traversal; test zoom and distance thresholds for popping/flicker.
5. Evaluate whether other distant landmass/vegetation impostors share the behavior, but do not assume the whole engine uses the island code or alter unrelated object types.

**Verification:** Reproduce Current ALT ~430–450 with legacy Forward, then Overview and each cinematic shot; repeat on Bigger and Massive and with ship yaw/roll, camera swaps, low↔high ascent/descent and off-center island positions. The proxy's apparent up should follow the same local curvature as ground/real mesh while presenting its face to the viewer when possible. If a physically oriented side image cannot represent an overhead view, document and separately scope a top-image/view-dependent sprite atlas or distance/angle rule. Test visible LOD transition, no seams/jumps, no unwanted world-position reset, acceptable 4GB performance. Require affected-machine browser visual check before marking verified fixed.

## VIS-LOD-002 — Future creator-programmable representation properties and altitude profiles

**Status:** **feature proposal**, not proof of a shipped feature or immediate fix prerequisite. **Priority:** P2 after VIS-LOD-001; design schema with extension seams now.

The user wants the 2D proxy to be a first-class reusable creator tool, not merely a hidden LOD shortcut. Expose via browser editing controls **and** independently usable programmer/agent API: stable representation ID and source object; semantic look/appearance preset; orientation mode (curvature-aware default, full camera-facing, world-locked, manual/custom), numeric tilt/pitch/yaw/roll, image look-at/facing mode, local-up and tangent references, position/anchor/scale, padding and actual silhouette bounds, padding fill/background color versus transparency, color tint, per-side/top shading/intensity, contrast/opacity, edge softness, lighting/depth behavior, silhouette material palette, transition distance/angle, size/quality budget and image/source atlas choice. Distinguish visible padding color from terrain/ocean color and alpha; do not “paint” the surrounding sky just to hide edge artifacts.

Allow optional configurations per **existing four atmospheric height bands** with smooth or explicit stepped interpolation; make clear whether values use observer altitude, object altitude, relative altitude, camera viewing angle, physical distance, or a combination. Height bands and distance LOD bands are orthogonal: an island can be near at high altitude or far at low altitude. Support an overhead/top view as a distinct authored/generated representation for genuinely top-down observation rather than pretending a side profile is correct from above. Preserve deterministic asset provenance and lightweight cache reuse.

Optional **Liquid Representation Mode:** user-programmed, event/state-linked tilt, orientation, shading, tint, padding/effects and transition controls with typed bounded inputs such as altitude, visual curvature, sunlight direction, viewer angle, weather or world events. In a Liquid editing UI hide ordinary controls in favor of target/context selectors and code/behavior surface while preserving original settings for return; the safe script/behavior runtime must have output validation and per-frame CPU/memory budgets, batched evaluation where feasible and fail-safe fallback. Do not run arbitrary untrusted JS from imported packages; do not require Liquid implementation to fix VIS-LOD-001. Keep definitions renderer-independent for future browser/native SDK consumption and expose programmatic inspection, relative/absolute edits, versioning and undo as the existing World API allows.

**Suggested next slices:** (a) curvature-correct island proxy + visual tests, (b) schema and numeric/padding/shading creator controls + four-band mapping, (c) overhead representation and angle-based selection, (d) bounded Liquid access + agent/programmer SDK conformance tests. Preserve all existing island geometry, source elevations and world positions throughout.
