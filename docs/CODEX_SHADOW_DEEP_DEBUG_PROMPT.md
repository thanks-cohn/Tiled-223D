## 1. Exact deliverables — an agent should be able to ask “WTF is that circle?” and answer from a capture

Integrate a dedicated, reusable `shadow/spatial visual diagnostics` module into the existing 3-mode `createSpatialDiagnostics` system and the existing trusted-click, time-limited `createSpatialDevelopmentController` facade. Prefer a small pure numerical collector plus thin THREE capture adapters, not a second renderer or a sprawling debug-only scene graph. Provide a versioned **trace contract** and an ordered module ownership/dataflow map.

Expose, through discoverable **read-only** inspection (suggested names, adapt to current API), these functions:
- `window.tiledSpatial.getShadowDiagnostics()` or `window.tiledSpatial.shadow.inspect()` — summary with explicit observation status in Performance, bounded current full state in Deep Debug.
- `window.tiledSpatial.shadow.getContributors({frameId?,viewportPoint?,region?})` — list candidate visible entities contributing to a selected screen circle/region, each with semantic ID and sampled bounds, not a false claim of GPU pixel attribution.
- Authorized `window.tiledSpatialDevelopment.shadowCapture({reason,...})`, `shadowHistory({limit})`, `shadowTransitionReport({beforeFrameId,afterFrameId})`, `shadowExplain({frameId,entityId?,region?})`, and optional `shadowIsolatePreview({entityId,visible})` / `shadowRestorePreview(id)`. Integrate with existing capture/replay/event/preview permission scopes; do not add an ambient privileged global or permit arbitrary asset or world mutation.

Each method must return bounded, JSON-serializable typed records with `schemaVersion`, exact `runId`, `frameId`, input world/scale ID, coordinate space + units, sample and status provenance, actual timestamp/commit/preset version where available, unsupported/unknown flags and a meaningful error code when data cannot be obtained. A disabled diagnostic should explicitly say disabled rather than silently compute “full truth” in Performance mode. Do not claim simulated occlusion is measured GPU truth.

## 2. Instrument the entire derivation chain, once per selected completed frame

**A. Physical/semantic source:** authoritative ship X/Y/Z and velocity, world ID/map dimensions, current vs previous scale preset (Current 500×500, Bigger 2500×2500, Massive 16000×16000), world wrap and relative ship/world position, ocean/water ID, surface height and normal *if actually sampled*, ocean-coverage sample coordinates/boolean outputs and mask coverage. Where current ocean is a flat canonical Y=0 surface, report that policy and its assumptions; do not invent a raycast surface hit or arbitrary `surfaceId`. Include actual active camera mode (Forward/Overview/Auto), mood weights/normalized altitude, source altitude field and the exact profile/planetRadius. Distinguish **physical** y from normalized atmospheric altitude and from rendered curved-earth y. Identify when an existing physical world-scale change legitimately changes canonical coordinates or projection by a declared scale transform.

**B. Shadow generation math:** actual `worldCenter`, `oceanIntersection`, projection policy (vertical-below), pre-/post-clamp radius, alpha, softness, elongation, color, `enabled`, `visible`, every named source field (active preset ID/schema/field path; mood interpolation weights; value of worldScale; height sample if any); all masks/gates and explicit reasons for invisible/fallback/clipped state. Give computed world-space extents, intended footprint bounds and checks if center/radius exceed intended limits. Capture the inputs/outputs of numeric model functions without changing their output in diagnostics-only work.

**C. Real rendered mesh/presentation:** actual mesh ID/name/type, parent chain, visibility/renderOrder, local position/rotation/scale, accumulated world transform matrix/bounds, backing radius and post-elongation extents, shader/horizon deformation uniforms, current floating origin and scale transform, render-layer and material flags (`color`, `opacity`, alphaMap/texture metadata, transparent/blending, depthWrite/depthTest, side, frustumCulled, material version). Report whether geometry/buffers/texture were reused/recreated after a transition, with named cause. Crucially record `state.radius` versus **effective rendered mesh radius**, `state.alpha` versus effective material/texture opacity; mark any mismatch. Sample visual boundaries after the curved horizon projection where feasible; never assume world scale == screen scale.

**D. Screen/camera projection:** record actual camera world pose, target/FOV/aspect/near/far and mode, viewport CSS and drawing-buffer pixels + DPR, world→floating-origin→horizon-deformed render→camera/clip→NDC→normalized viewport/CSS pixel chain. Project center **and enough actual boundary points** to report oriented screen ellipse/area, not just center or a radius guessed from distance. Include behind-camera, depth/near/far, far-hemisphere/culling, clipping and likely occlusion status with `unknown` where depth/GPU evidence is unavailable. Capture the physical ship's projected position, shadow center/edge and expected pixel separation in the same completed frame.

**E. Other circular contributors — essential:** give stable IDs and separate capture records for the **base ocean/globe surface**, any local ocean geometry/patch, shadow mesh, near/medium/planetary tonal ribbons, atmospheric/fog/sky effects and other large projected blue meshes that overlap the selected viewport region. Record each contributor's geometry/source, world position, world-radius or actual bounds, scale, color/material, opacity and viewport bounds. Use cheap broad-phase filtering (known relevant ocean objects first, inspect only selected neighborhood in Deep Debug); never assume one projected disk is a shadow. If object-space attribution cannot distinguish transparent GPU compositing, report candidate draw-order/overlap plus `pixelAttribution: "unverified"`.

## 3. Transition causality and anomaly reports

Bounded per-frame history must support comparing (a) stationary hover and ascent, (b) LOW↔MIDDLE↔HIGH↔TOP mood blends near the creator's displayed ALT ~374, (c) Forward/Overview/Auto camera changes, (d) 500↔2500↔16000 scale switching including **expansive→500**. Add explicit structured cause categories: physical travel, physical altitude change, preset/mood mix, profile/world scale transform, floating-origin shift, camera pose/FOV, source model change, world-vs-mesh transform, mesh recreation, material/alpha/texture update, shore/depth mask, viewport resize/DPR, uncertainty. A large screen-space circle change with stable physical state is not automatically a world-space jump: inspect projection, geometry and materials.

Anomaly detectors with **tolerances based on units, dt, scale transforms and camera movement**, not unexplained fixed screen thresholds, should flag: unexpected shadow world-anchor discontinuity, effective-mesh-radius mismatch, radius/opacity spikes not explained by altitude/preset, shadow texture/material/mesh duplicate, wrong mesh parenting or floating-origin subtraction, projected circle unexpectedly filling viewport, shadow crossing masked shore/far side, unexpected overlap with other blue circular entities, frame mismatches and missing/invalid numeric inputs. Distinguish WARNING (suspected) from CONFIRMED based on evidence. In true world-size switches, test **preserved relative location and declared mapping** rather than asserting absolute X/Y/Z or radius remain numerically identical.

Provide exact before/after causes and 2–3 safe next diagnostic actions in `shadowExplain()`; do not silently change ocean/shadow parameters to hide an artifact. If evidence implicates non-shadow geometry, say so explicitly and identify source module.

## 4. Low overhead and access boundaries

- **Performance/user mode:** only the numeric operations REQUIRED to draw the existing ocean/shadow. NO debug frame object creation, projected boundary sampling, scene traversal, deep clones, JSON serialization, GPU readback, new per-frame logs, new texture/geometry allocation, or an extra animation/update loop. The module is lazily initialized or cheaply bypassed; assert zero new tracing captures/counters in Performance. A normal rendering `getFootprintState()` may reuse already-computed lightweight state; it must not turn on Deep Debug implicitly.
- **Debug (light):** optional low-frequency compact numbers only, e.g. active altitude/mood + actual effective shadow width/candidate entity count, without full matrices, per-vertex traces or per-frame captures.
- **Deep Debug:** lazily collect full state **on explicit capture**, with an optional short bounded event/history session (sampling cadence and capacity exposed). Honor preexisting limits and developer authorization; use ring buffers and byte/frame/time caps, avoid full-scene serialization and screen-sized buffers. Reuse the existing render frame ID and next-completed-frame synchronization. A captured pair should be self-contained, suitable for a pasted JSONL excerpt + user screenshots in a future ChatGPT turn.
- Read-only shadow measurements may be exposed under `tiledSpatial` with mode restrictions; image capture, replay, isolating one visual effect, export and mutating previews stay inside the existing trusted user click/15-minute scoped `tiledSpatialDevelopment` permission boundary. Isolation must be reversible, display-only and incapable of changing terrain, height, collision, ship physics, map/GLB data, preset defaults or other worlds.
- Avoid screenshot/PDF binary artifacts in Codex patch submissions; export **text-only JSON/JSONL** fixtures in repo. If a PNG was captured for local review, keep it outside a patch if binary uploads are unsupported; record provenance honestly.
