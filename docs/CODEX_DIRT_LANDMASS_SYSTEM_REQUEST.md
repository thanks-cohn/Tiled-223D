## Goal and nonnegotiable boundaries

Produce **one saved, canonical new dirt landmass in the original 500 × 500 Tiled-relative world**; preserve both original islands exactly (semantic ground, elevations, grass/sand/trees/materials, relative placement, collision and authored destinations). The dirt landmass is additional geography taking approximately one-third of the initial example map's **overall** area, subject to no-overlap constraints; its coverage, position and outline become editable canonical map data. If one-third cannot fit while protecting all authored features and clearances, return an explicit capacity/placement diagnostic and alternatives, rather than recoloring an island, silently squeezing it, changing its original location, or pretending an unrelated independent ellipse in each world is the same source. The generated canonical region must be persisted alongside / as a non-destructive addition to the same editable Tiled project, with stable provenance and an ordinary Tiled-compatible export/adapter; do not overwrite user map bytes without an authorized reviewed commit.

The Current 500 × 500, Bigger 2,500 × 2,500 and Massive 16,000 × 16,000 interpretations are **three views/scale mappings of the same saved canonical landmass**. The Tiled map's relative geographic footprint, outline, orientation and placement are preserved in each world overview. A small authored patch stays small on each exterior overview even when its *interior journey* is huge. **The ramps do not change size, shape, collision profile, count, orientation, ID or sequence** when switching world sizes; the safe, drivable distance between their protected footprints changes. Do not multiply ramp geometry by the world-scale factor and do not independently reroll ramps/continent per scale.

There are TWO expansion concepts: (1) selected world dimensions/default traversal behavior; (2) landmass-specific *experience* expansion. A landmass either **inherits** the selected world's expansion profile or **replaces** that profile with ONE chosen alternative, including an ocean-like profile on a 500 × 500 world. A replacement does not stack/multiply on top of the inherited world profile. Dirt-surface-specific traction/height/visual tuning is separate from choosing an expansion profile and must not secretly add another expansion multiplier. A detailed forest-only destination/experience remains journey-only by default; it is not automatically exposed as an exterior-flight destination just because the engine knows its identity.

## Exact artistic and procedural default

Generate and save a mostly flat, spacious, naturally varying dirt plain with broad predominantly medium-brown patches, lighter-brown patches, a smaller amount of dark brown and occasional subtle outlines. Keep most shading differences in material/color rather than elevation. Use bounded smooth height variation, a few intentional high points and drivable inclines, not accidental wall-like noise. All visible near terrain and physics must sample the same authoritative height/feature representation. Ocean stays visually distinct; original islands retain their original grass/sand palette.

Generate large/medium/small ramps **once on the canonical 500 × 500 production** with initial probabilities **5% / 3% / 10% per eligible, adequately separated candidate zone**. These are NOT percentage-of-total-land-area guarantees; distinguish the two metrics in all UI, API and reporting. Persist ramp IDs, exact canonical shapes/dimensions, orientations, collision footprints, approach/landing envelopes and placement. Ensure reasonable sparse spacing with type-specific exclusion radii, no clusters, no ramp under an island, road intersection, authored destination or water/shoreline, and ample high-speed approach/recovery corridors. Never generate a new random ramp each time the ship approaches or the player switches worlds. Creator edits to probabilities trigger only an explicit, reviewable canonical regeneration request; show IDs added/removed/moved beforehand.

## Required architecture and contracts

### 1. Canonical world and saved production

Use the existing semantic map/import/export model and world API's protected-base, region-identity and revision concepts where applicable. Design a versioned canonical landmass record: source map ID/revision, stable landmass ID, authored 500 × 500 footprint/mask/outline, signed origin and transform, default soil material palette/seed, base elevation/variation constraint, protected no-build zones, stable fixed-feature list, route/interval graph and attached authored edits. Persist the concrete ramp records and deterministic recipe. Separate storage of geographic source, derived expansion-plan metadata and throwaway rendered meshes. Version deterministic algorithms so loading an old save does not silently change its terrain. An authored patch overlay must survive cache eviction and regeneration.

### 2. Expansion interpreter

Maintain two explicit mappings: canonical Tiled/world overview position, and on-ground **experience-local** route/terrain coordinates. Build stable monotone/invertible route progress mappings with protected feature footprints held physically constant and extra distance allocated **between** them. Provide an extendable policy for 2D traversable land (more than one road): route/corridor graph plus continuous safe local warp, preserving feature neighborhoods and intersections. Never silently use a 1D route coordinate to distort arbitrary 2D terrain. If topology, clearance, feature overlap, inverse mapping or available budget is incompatible, return a precise diagnostic and do not mutate.

For each protected feature interval `[a_i,b_i]`, physical length remains `b_i-a_i`; for each permitted gap, experienced length equals original gap plus allocated nonnegative additional distance. The same ramp can sit at different experienced-progress percentages depending on gap expansion without moving in canonical overview space. World-size changes may change **gap lengths**, never the ramp. Preserve entrance/exit/landmark anchors, reversing, turning and explicit world↔experience transitions. Do not scale the original islands with the new landmass or redraw them as dirt.

### 3. Deterministic bounded streaming for 4 GB devices

Generate the canonical production once and save it. Resolve a compact expansion plan by source/profile revision; reconstruct deterministic terrain chunks by `landmassId + sourceRevision + effectiveProfileVersion + intervalId + chunkIndex (+ spatial branch)`. The renderer may unload/rebuild vertices, but the world does NOT change. No 2,500² or 16,000² detailed height/ground allocation. Near: collision-ready mesh/ramps and authoritative samples. Mid: cheaper coherent geometry/landmarks. Far/orbit: canonical map-aligned low-cost footprint and broad color. No overlapping coarse/near z-fighting or holes along coastlines; plan stable LOD morph/blends or conservative clipping. Prioritize bounded CPU time/mesh upload/JS heap/GPU memory on an approximately 4 GB Windows computer, with a small eviction cache, incremental build budget, and speed/steering-aware forward prefetch. High-speed driving must never collide with an unprepared, invisible or fictitious ramp; use safe fallbacks and observable diagnostics.

### 4. First-class programmer AND agent API

Create the **root directory `API/Dirt/`** as the readable API reference, NOT a second unconnected physics implementation. Build two first-class typed/JSON surfaces over ONE versioned dirt-world core, preserving existing `ProgrammerWorldApi`/`AgentWorldApi` contracts and actor/permission/revision/atomic-commit/undo semantics as far as compatible. If existing version-1 schemas cannot safely express the new operations, extend via a separately versioned dirt capability and do not break existing v1 clients. A programmer receives exact low-level controls for canonical data, constraints, feature/gap mapping, visual and collision profile, inspection and edits. An agent receives equally capable bounded inspect/explain/plan/preview/validate/commit/undo/diagnostics tools, with high-level intent planning that compiles to the same reviewable operations; neither is a fake thin wrapper or an LLM service prerequisite.

Implement a real callable local JS surface, a bounded CLI/JSON adapter consistent with `scripts/world-api-cli.mjs`, and documented `API/Dirt/COMMANDS.md` with **actual tested invocations**. If a browser global is added, document its security and lifecycle limits; do not claim browser-console methods automatically exist in CLI or Codex's execution environment. No runtime code in Markdown; no fictitious “implemented” buttons or commands. A future MCP/desktop adapter can call the same validated core but is NOT necessary to ship the browser-first slice.

For **every meaningful adjustable parameter**, support `inspect` (actual and effective values with provenance), `explain` (why effective value/visibility/LOD/collision differs), `plan` (read-only), `validate` (typed diagnostics), explicit atomic `commit` with expected revision/actor grants, `preview` (bounded, non-mutating) and `undo` (permission-checked). Include finite range/type checking, stable IDs, pagination, bounded region/query cost, cost forecasts, source/derived map comparisons, deterministic regen dry run with feature-diff, and machine-readable errors with relevant sample coordinates, nearest feature, conflicting interval and suggested safe parameter ranges. No agent can bypass protected-island/source ownership rules using a hand-crafted direct operation. All mutation paths must revalidate on commit, reject stale revisions and provide readable failure reasons.

### 5. Debugging from the same API

An agent must be able to query the current displayed/collision sample at a coordinate and identify its source (canonical cell, procedural dirt, saved ramp, authored override, ocean, visual LOD), physical height, sampled shade, world/experience coordinates, source/profile revision, active scale, nearest feature/interval, caching/build status, resolution/LOD and collision-authority status. Add paged or bounding-box-limited trace of exact expansion mapping decisions, ramp placement rejection/spacing rationale, chunk build/unload, coastline occlusion, large/small world parity, map-footprint mismatch and previous collision/terrain seam observations. Explain where physical and rendered surfaces disagree rather than hiding it. Provide an optional minimal reproducible diagnostic bundle with seed/config/version, bounded source snapshot, sampled coordinates/trace, visual+collision metrics and safe environment metadata; redact private paths/content by default, impose size limits and never silently upload. This must help future programmers/agents debug WITHOUT digging through full 16k maps or editing core code for each question.

### 6. Human editor and native project shape

Make one compact, friendly landmass editor backed by the exact same schema and operations: select the canonical region; see a map footprint in all three scales and a ground-level before/after preview; inherit-world versus replace-profile switch; world-scale selector; ramp density per *eligible candidate zone*, minimum clearances, flatness, high points, color-patch shades, material outline, maximum terrain detail/cost, and regeneration warnings. Sliders plus exact numeric input; plainly label effective inherited vs overridden values, preview/revert/restore defaults, and highlight infeasible choices. The default must be intentionally enjoyable with zero configuration, but every artistic setting must be inspectable and editable. Do not implement a large unrelated UI framework or let editor controls mutate state without an authorized, revisioned commit.

- Shared programmer and agent APIs return truthful capabilities, stable inspect/provenance, bounded preview/trace/cost, protected edits, revision-safe atomic commit/undo and actionable machine-readable diagnostics. Document exact tested call syntax at `API/Dirt/COMMANDS.md`.

**Final implementation principle:** The source map defines WHERE this is; the canonical production defines WHAT exists; the selected, single effective expansion profile defines HOW FAR it feels; the renderer decides only WHAT TO DRAW NOW. The API must make all four layers inspectable and safely editable by humans, programmers and authorized agents.
